# ADR-0003: Стабильный выбор инстанса при дубле workspace в реестре

## Status
Accepted — 2026-06-01

## Context
Реестр живых окон (`instances` в `bot.db`) ключуется по имени workspace.
Бот собирает рантайм-список в `tg-bot/bridge/registry.py`
`load_runtime_instances()`, дедуплицируя ряды с одинаковым ключом. Входящая
маршрутизация (`bot/messages.py` `_resolve_topic_target`) на **каждое** сообщение
зовёт `refresh_instances()` → `load_runtime_instances()` и берёт из
дедуплицированного списка инстанс по `cwd == workspace_id`. То есть выбор окна
целиком определяется тем, кого оставил дедуп.

Прежняя логика: `storage.get_instances()` отдаёт ряды `ORDER BY heartbeat_at ASC`
(старейший heartbeat первым), а дедуп делал `instances_by_key[key] = instance` —
**побеждал последний по свежести heartbeat**. Warning писался только когда у двух
рядов с одним ключом **различались** cwd.

Проблема проявляется, когда **одна папка открыта в двух живых окнах** (например
VS Code-расширение + npm-CLI `claude`, оба на одном и том же воркспейсе). Оба ряда
имеют одинаковый cwd и **оба heartbeat'ят свежо** (~15 с) — их heartbeat'ы
обгоняют друг друга, поэтому «свежайший» победитель **скачет между окнами на
каждом refresh**. Входящие в топик раскидывает по обоим окнам; в том окне, что
смотрит пользователь, оказывается лишь часть («из трёх сообщений дошло одно»).
Дубль с одинаковым cwd при этом глушился молча — warning не срабатывал, и баг был
невидим в логах. Инцидент: 2026-06-01, топик `infra`.

Триггер дублей — жёсткая смерть окна (OOM-краш VS Code, см.
[runbook](../runbooks/duplicate-window-message-split.md)): она не вызывает
`unregisterInstance()`, ряд висит до реапинга (~45 с), и переоткрытие окна в это
окно времени даёт второй живой ряд.

## Decision
Победитель при коллизии ключа выбирается по **стабильному** признаку, а не по
свежести heartbeat:

```
winner = max по (int(started_at), -port)
```

- `started_at` — непрозрачный per-OS токен времени создания процесса, **фиксирован
  на всю жизнь процесса** → победитель не меняется между refresh'ами, и инбаунд
  перестаёт пинг-понговать между окнами.
- Reload (то же окно перезапустилось) по-прежнему отдаёт победу новому процессу:
  у него `started_at` позже; старый ряд вскоре реапится по dead-PID/протухшему
  heartbeat.
- Меньший `port` ломает ничью, так что выбор детерминирован даже при равных/пустых
  токенах. Пустой/нечисловой `started_at` → `0`, чтобы ряд без токена не затенял
  ряд с токеном.

Дополнительно дедуп теперь **громко логирует** обе коллизии:
- одинаковый cwd → `workspace … has two live windows (ports …) — routing to the
  later-started one; close the extra window` (это и есть причина «сообщения
  доходят через раз» — делаем её видимой);
- разный cwd → прежний warning «keep one; rename the other».

Изменение целиком в **боте** (`tg-bot/bridge/registry.py`). **Плагин не менялся.**

## Consequences
- Плюс: маршрутизация в топик при двух живых окнах на одну папку стабильна — все
  сообщения идут в одно окно, а не делятся.
- Плюс: дубль виден в логах бота сразу, диагностируется без раскопок в `bot.db`.
- Плюс: семантика reload сохранена (новый процесс выигрывает у умирающего старого).
- Минус: бот по-прежнему не может знать, *какое* из двух окон смотрит пользователь
  — он лишь делает выбор детерминированным и заметным. Операционно правильно
  держать **одно окно на папку**; код только защищает доставку.
- Требует рестарта роутер-бота, чтобы подхватить новый код.

Проверено: `python -m py_compile bridge/registry.py` — OK; юнит-тест с двумя рядами
с обгоняющими друг друга heartbeat'ами — победитель неизменен на обоих refresh'ах.

## Alternatives Considered
- **Оставить «свежайший heartbeat».** Текущая регрессия — флип-флоп между двумя
  живыми окнами. Отклонено.
- **Выбор по свежайшему heartbeat, но только среди не-протухших + fan-out в оба
  окна.** Дублировал бы инбаунд в обе сессии; пользователь видел бы каждое
  сообщение дважды (в двух окнах). Отклонено как более запутанное, чем стабильный
  единственный получатель.
- **Запретить регистрацию второго окна на тот же cwd на стороне плагина**
  (self-dedup при старте). Сильнее — давит размножение в корне, но ломает reload
  (новый процесс должен заменять старый) и требует различать «живой сосед» vs
  «протухший остаток». Возможное будущее усиление; вне объёма этого решения.
